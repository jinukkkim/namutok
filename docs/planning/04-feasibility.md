# 4단계 — 실현 가능성·리스크 (2026-11-18)

> 확인 방법: 가정집 회선 `curl`(브라우저 UA, 1.2~1.5초 간격), 데이터센터 IP 요청 1회(웹 가져오기 도구), `sidebar.json` 6회 샘플링(30초 간격), 편집 중 문서 30건의 og 태그 수집, 나무위키 이용약관 브라우저 렌더링. 직접 확인은 `[원문 확인]`, 검색 결과로만 본 것은 `[검색 스니펫]`, 계산·판단은 `(추정)`으로 표시했다. 경쟁·운영사 리스크의 근거는 `03-competition.md`에 있다.

## 요약
- **만들 수 있다.** 기술과 약관 어느 쪽도 Kill 기준에 걸리지 않았다. 데이터센터 IP에서도 문서와 `sidebar.json`을 받았다(단 Vercel 자체는 미확인).
- **카드 재료는 편집 중 문서가 랜덤보다 낫다.** 대표 이미지 30/30, 메타로 시작하는 요약 5/30(모두 "파일:" 접두어라 잘라내면 된다). 주제도 지금 관심사 쪽으로 쏠린다.
- **운영비 0원으로 하루 약 1,000세션까지 버틴다** (추정). 무료 한도를 넘으면 과금 대신 멈추므로 0원 조건은 깨지지 않는다.
- **가장 큰 리스크는 여전히 운영사의 접근 정책이다.** 기술 해법은 없고, 감지·안내·대체 경로로 피해를 줄일 뿐이다.

## 1. 기술

### 1.1 A1. 나무위키 원문을 실시간으로 가져올 수 있는가 → **가능 (Vercel IP만 미확인)**

| 확인 항목 | 결과 | 근거 |
|---|---|---|
| 공개 API | 없음. 문서 내용을 주는 JSON API는 찾지 못했다 | 1단계 검색, robots.txt `[원문 확인]` |
| 브라우저에서 문서(`/w/`)를 바로 요청 | **불가**. `Access-Control-Allow-Origin` 헤더가 없다(CORS) | 응답 헤더 `[원문 확인]` |
| 서버에서 문서 요청: 가정집 IP | **가능**. 10건 중 10건 HTTP 200, 캡차 없음. 서버는 nginx | `[원문 확인]` |
| 서버에서 문서 요청: 데이터센터 IP | **가능**. 웹 가져오기 도구(데이터센터 IP)로 `/w/버거킹`과 `/sidebar.json` 모두 HTTP 200, 실제 본문·JSON, 차단·챌린지 페이지 없음 | `[원문 확인]` (2026-11-18) |
| 차단 정황 | 2026-10-08경부터 비공식 뷰어가 모바일 데이터 망에서 Cloudflare 차단("Sorry, you have been blocked")을 받고 있고, VPN 대역 차단 정황이 있다. **Vercel·Cloudflare Workers IP 자체는 아직 테스트하지 않았다** | [나무뷰어-리팩 리뷰](https://play.google.com/store/apps/details?id=com.monpub.namuwiki.repack&hl=ko&gl=KR&showAllReviews=true) `[원문 확인]` (3단계) |
| 문서 HTML 구조 | Vue SSR, 문서 하나에 약 250KB. **og 태그(`og:title`, `og:description`, `og:image`)가 매번 있다**. 본문 클래스명은 해시라 파싱이 깨지기 쉽다 | `[원문 확인]` |
| 대표 이미지 | 문서마다 다른 `og:image`(`i.namu.wiki`). 외부 Referer로도 200이라 핫링크가 막혀 있지 않다 | `[원문 확인]` |
| `/sidebar.json` | 브라우저에서 바로 요청 가능(`Access-Control-Allow-Origin: *`), robots.txt 허용 | `[원문 확인]` |
| `/random` | robots.txt가 허용하지 않는다. 서버에서 쓰지 않는다 | `[원문 확인]` |
| iframe | 불가(`X-Frame-Options: SAMEORIGIN`). 원문은 새 탭으로 연다 | `[원문 확인]` |

### 1.2 `sidebar.json` 실측 (2026-11-18, 30초 간격 6회)
| 항목 | 값 |
|---|---|
| 한 번에 주는 항목 수 | 항상 15건 |
| 응답 형식 | `{"document": 제목, "status": "normal", "date": 유닉스 시각}` (status는 6회 모두 normal) |
| 30초 뒤 겹치는 항목 | 15건 중 0~4건 → 30초마다 거의 전부 새 문서 |
| 편집 속도 | 3.3분 동안 서로 다른 문서 76개, 분당 약 25건 (추정) |
| 하위 문서(`/` 포함) | 76건 중 19건(25%) → 피드에서 뺀다 |
| 이름공간 문서(틀·분류·파일·사용자) | 0건 (이 샘플에서는 이미 제외돼 나오는 것으로 보인다, 추정) |

→ 30초마다 폴링하면 하위 문서를 빼고도 한 번에 약 11건의 새 카드 후보가 생긴다. 15건만 주기 때문에 30초보다 느리게 폴링하면 중간 편집을 놓치지만, 피드 용도로는 문제가 없다.

### 1.3 편집 중 문서의 카드 품질 실측 (A4)
하위 문서를 뺀 편집 중 문서 30건의 og 태그를 받았다.

| 항목 | 편집 중 문서 (30건) | 랜덤 문서 (1단계, 10건) |
|---|---|---|
| `og:image` 있음 | **30/30** | 10/10 |
| 요약이 메타·너무 짧음 | **5/30 (17%)**. 5건 모두 "파일:xxx.jpg"로 시작 → 첫 토큰만 잘라내면 된다 | 4/10 (40%). "파일:", "분류:", 표 머리글 |
| 주제 | 애니·만화(사랑에 빠진 판다, 북두의 권 3건), 아이돌(베스티, 키리), 신곡(Gleam Hour, 2026-11-23 발매), 야구(김규성, 이지영, 제이스 영), 게임(니케, 블래키, 스카이본), 정당 4건, 국가 관계 3건 | 1894년생 야구 선수, 미국 하원의원 선거 표 등 |

- 해석: 편집 중 문서는 **지금 누군가 관심을 쏟는 주제**라 랜덤보다 카드가 재밌을 가능성이 높다 (추정, 사용자 반응은 미검증).
- 발견: 같은 편집자가 관련 문서를 연달아 고치는 **편집 흐름**이 보인다(북두의 권 3건, 시에라리온 관계 3건, 정당 4건). 그대로 두면 같은 주제가 연달아 나온다. "지금 누군가 북두의 권을 정리하는 중" 같은 묶음 카드로 바꾸면 오히려 재미 요소가 될 수 있다 (4b에서 결정).
- 정제 규칙: 앞쪽 "파일:\S+" 토큰 제거, 연속 공백 정리(`" 일본의  학원 ,  로맨스  만화"`처럼 링크 자리에 공백이 남는다), 25자 미만이면 제외.
- 미확인: `og:image`가 기본 로고 같은 대체 이미지인 경우를 따로 가려내지 않았다. 30건 모두 문서별 URL이었다.

### 1.4 MVP 구조안 (무엇을 어디서 처리하나)
| 위치 | 하는 일 |
|---|---|
| 브라우저 | `sidebar.json`을 30초마다 직접 받는다(CORS 허용, 서버 비용 0). 하위 문서·중복·이미 본 문서를 뺀 제목 큐를 만든다. 좋아요·본 문서·분류 점수는 localStorage에 둔다 |
| 서버 함수 `/api/card?title=` | `/w/<제목>`을 받아 og 태그 3개만 뽑고 정제해 약 1KB JSON으로 돌려준다. head 부분만 읽고 끊는다. `Cache-Control: s-maxage=21600, stale-while-revalidate`로 CDN이 같은 문서를 6시간 캐시한다 |
| 이미지 | `i.namu.wiki` 핫링크. 흐림·끄기 토글. 우리 서버로 이미지가 지나가지 않는다 |
| 랜덤 탭 | 세션 동안 모인 제목 풀과 빌드 때 넣는 시드 목록에서 뽑는다. "진짜 랜덤" 버튼은 `namu.wiki/random`으로 가는 링크 |
| 장애 대응 | `sidebar.json` 실패 → 제목 풀 순환과 안내 배너. `/w/`가 403이나 챌린지 페이지를 돌려주면 "나무위키 접속이 제한되고 있다" 화면 |

- 나무위키에 가는 요청은 **사용자 수가 아니라 편집 속도와 캐시에 묶인다**. 최악의 경우에도 새 문서 수(분당 약 25건)를 넘지 않고, 아무도 안 보면 0이다 (추정).
- 프록시는 표준 `fetch`만 써서 Vercel과 Cloudflare Workers 사이를 옮길 수 있게 둔다.

### 1.5 가장 어려운 부분
1. **Vercel IP에서의 차단 여부(A10).** 데이터센터 IP 1곳은 통과했지만 호스팅사마다 다르다. MVP 첫날 프록시부터 배포해 확인하고, 막히면 Kill 기준대로 멈춘다.
2. **카드 품질 정제.** 정제 규칙은 단순하지만 예외(동음이의어 문서, 리다이렉트, 표로 시작하는 문서)를 계속 손봐야 한다.
3. **사이트 변경 대응.** 본문 HTML은 자주 바뀐다(3단계: 리팩 2026년에만 세 번 고장). og 태그만 쓰는 것으로 위험을 줄인다. og 태그가 안정적인지는 미검증이다.
4. **1주 일정.** WikiTok은 2시간이었지만 namutok에는 프록시, 정제, 장애 대응이 더 붙는다.

## 4. 콜드스타트
- **단면 시장이다.** 사용자가 콘텐츠를 만들 필요가 없다. 나무위키 편집자들이 분당 약 25건씩 피드를 채운다. 첫 사용자부터 가치가 있다.
- 네트워크 효과도 없다. 그래서 사용자가 늘어도 제품이 좋아지지 않는다. 유입은 공유 카드와 커뮤니티 공개(5단계)에 달려 있다.

## 반대 의견
1. **"막는 조항이 없다"와 "허용된다"는 다르다.** 운영사는 소송 대신 reCAPTCHA, Cloudflare, 실검 API 암호화 같은 기술적 차단을 반복해 왔다. namutok이 뜰수록 요청이 늘고 차단 확률도 오른다. 성공 시나리오와 차단 시나리오가 겹친다.
2. **데이터센터 IP 테스트는 절반만 했다.** 웹 가져오기 도구의 데이터센터 IP는 통과했지만 Vercel IP 대역은 다를 수 있다. 서버리스 환경에서 막히면 운영비 0원으로는 우회할 방법이 없다(가정용 프록시는 유료이고 우회 성격이다). 그러면 Kill 기준에 해당한다.
3. **편집 중 문서의 품질이 "재미"로 이어진다는 보장은 없다.** 30건 중 정당 4건, 국가 관계 3건처럼 건조한 정리 작업도 많다. 편집이 활발하다고 사람들이 넘겨 보고 싶은 문서는 아니다. 실제 사용자 반응은 아직 하나도 없다.
4. **하루 1,300세션 한도는 바이럴 한 번이면 넘는다.** WikiTok은 최대 약 20만 명이 몰렸다(3단계). 그 순간 Vercel이 30일 정지되면 가장 중요한 시기에 서비스가 꺼진다. 0원 조건과 "실사용자 유치" 목표가 이 지점에서 부딪친다.
