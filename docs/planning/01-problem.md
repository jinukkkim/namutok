# 1단계 — 문제·목적·제약

## 한 줄 정의
나무위키 헤비 유저가 "랜덤 문서" 버튼을 반복해서 누르며 시간을 보내던 경험을, 틱톡처럼 세로로 넘기는 피드로 바꿔 주는 무료 웹 서비스.

## 입력 유형
대략적인 아이디어다. 해결 방식(WikiTok 형식 + 나무위키 콘텐츠)은 정해져 있지만, 대상, 사용 순간, 제약이 비어 있어 질문으로 채웠다.

## 참고: WikiTok 분석 (2026-11-18)
- **배경**: 뉴욕 개발자 Isaac Gemal이 2025년 2월에 만들었다. 바이럴 트윗에서 아이디어를 얻었고, Cursor와 Claude로 2시간이 안 걸려 프로토타입을 만들었다. 코드는 수백 줄 규모다. "추천 알고리즘 없음"과 "숏폼 대신 지식 스크롤"이라는 메시지로 여러 나라 언론에 보도됐다. ([Tubefilter](https://www.tubefilter.com/2025/02/11/wikitok-tiktok-wikipedia-scrolling-learning-project-isaac-gemal/), [PC Gamer](https://www.pcgamer.com/hardware/give-your-wikipedia-rabbit-hole-deep-dives-a-dollop-of-dopamine-by-reading-them-in-an-anti-algorithm-tiktok-style-feed), [GeekNews](https://news.hada.io/topic?id=19059))
- **구조**: [GitHub 소스](https://github.com/IsaacGemal/wikitok)를 받아 직접 확인했다. MIT 라이선스이고 마지막 커밋은 2025-03-17이다.
  - React 18, Vite, Tailwind로 만들었고 **백엔드가 없다**. 브라우저에서 위키백과 API(`generator=random`, `origin=*`)를 바로 부른다.
  - 랜덤 문서 20개를 한 번에 받는다. 문서마다 앞 5문장과 800px 썸네일만 가져오고, **썸네일이 없는 문서는 버린다**. 이미지를 미리 받아 다음 묶음을 준비해 둔다.
  - 세로 스와이프는 CSS scroll-snap으로, 무한 스크롤은 IntersectionObserver로 만든다. 그 외 기능은 좋아요 목록, JSON 내보내기, 공유, PWA, 48개 언어 선택이 전부다.
  - **한국어 위키백과를 이미 지원한다** (`languages.ts`에 `ko.wikipedia.org`가 있다).
- **시사점**: WikiTok이 2시간 만에 나올 수 있었던 것은 무료 공개 API가 있었기 때문이다. namutok에는 이 전제가 없다(아래 반대 의견 1).

## 문제 상세
- 나무위키는 한국 인터넷에서 가장 많이 쓰이는 위키이고, 한국어 위키백과는 문서 수와 깊이에서 나무위키에 못 미친다는 것이 사용자의 판단이다 (2단계에서 트래픽 근거로 검증).
- 나무위키 헤비 유저는 정보를 찾을 때만 나무위키를 쓰지 않는다. 심심할 때 랜덤 문서나 연관 문서를 따라가며 시간을 보내기도 한다 (추정, 2단계에서 검증).
- 하지만 나무위키의 탐색 방식은 "랜덤 버튼 누르기 → 긴 문서 → 뒤로 가기 → 다시 누르기"를 반복하는 것이고, 숏폼에 익숙한 사용자에게는 마찰이 크다 (추정).
- WikiTok은 이 경험을 위키백과로 풀었다. 하지만 한국어 위키백과 콘텐츠로는 나무위키 사용자의 관심(서브컬처, 인물, 밈, 드립)을 채우지 못한다.

## 페르소나
**"새벽 2시의 나무위키 유저", 20대 대학생 또는 직장인**
- 하루에도 여러 번 나무위키를 연다. 검색으로 들어갔다가 연관 문서 링크를 따라가며 30분씩 보낸다.
- 유튜브 쇼츠와 인스타 릴스도 보지만, 나무위키 특유의 TMI와 드립이 더 재밌다고 느낀다.
- "랜덤 문서" 버튼을 눌러 본 적이 있지만, 고르지 못한 결과(동음이의어 문서, 짧은 문서 등)를 여러 번 넘겨야 해서 귀찮다 (추정).

## 현재 대체재
| 대체재 | 한계 |
|---|---|
| namu.wiki의 랜덤 문서 기능 | 문서 전체가 열려 한 번에 하나씩만 볼 수 있고, 다음 문서로 넘기는 흐름이 없다 |
| [나무뷰어](https://apps.apple.com/KR/app/id993035669) (비공식 뷰어 앱) | 랜덤 문서 바로가기는 있지만 세로 피드는 아니다 |
| WikiTok (한국어 위키백과 선택) | 콘텐츠가 위키백과라 나무위키 사용자의 관심사와 맞지 않는다 |
| 유튜브 쇼츠, 인스타 릴스 | 시간 때우기 수요를 가져가지만 "읽는 재미"는 없다 |

## 해결책 후보
| # | 후보 | 한 줄 설명 |
|---|---|---|
| 1 | **랜덤 피드 (기본형)** | 나무위키 랜덤 문서를 제목 + 개요 몇 줄 + 대표 이미지 카드로 세로 피드에 보여주고, 탭하면 원문으로 이동한다. WikiTok을 그대로 옮긴 형태다 |
| 2 | **화제 문서 피드** | 무작위 대신 나무위키 인기 검색어와 최근 많이 수정된 문서로 "지금 뜨는 문서"를 넘겨 본다. 헤비 유저의 "요즘 무슨 일?" 수요를 노린다 |
| 3 | **분류 피드** | 게임, 애니, 인물, 역사처럼 나무위키 분류를 골라 그 안에서만 랜덤으로 넘긴다. 덕질 대상별 피드다 |
| 4 | **토끼굴 모드** | 카드 안의 링크를 따라 연관 문서를 이어서 보여준다. 나무위키 특유의 "정신 차려 보니 새벽 3시" 경험을 피드로 만든다 |
| 5 | 덤프 기반 큐레이션 피드 | 실시간 대신 공개 덤프를 가공해 피드를 만들고 원문 링크를 단다. 최신성이 떨어진다. **사용자가 실시간 확보가 막히면 접겠다고 해서 보류** |

## 목적·제약
- **목적**: 포트폴리오, 그리고 실사용자 유치
- **무료 범위**: 사용자 무료이고 운영비도 0원이다(무료 티어 안에서만 운영). 광고와 결제는 없다. 나무위키 라이선스의 NC(비영리) 조건과도 맞는다.
- **시간**: 빠르게 출시한다. 1주가 목표다.
- **기술·형태**: 웹/PWA (React/Next.js)
- **첫 타깃**: 나무위키 헤비 유저
- **Kill 기준 (사용자 결정)**: 나무위키 원문을 실시간으로 가져오는 것이 막히면(기술 또는 약관) 접는다.

## 반대 의견
1. **데이터 확보가 1단계부터 막힐 수 있다.** 나무위키 공개 API는 찾지 못했다. 브라우저에서 바로 부를 수 없으면(CORS) 서버 프록시가 필요한데, 그러면 사실상 크롤링이 된다. 봇 차단이나 약관 위반에 걸리면 사용자가 정한 Kill 기준에 바로 해당한다. WikiTok이 쉬웠던 이유가 namutok에는 없다.
2. **나무위키 문서는 카드 형식에 맞지 않을 수 있다.** 목차, 틀, 각주, 동음이의어 문서가 많고, 개요가 없거나 "이 문서는 ~에 대해 다룹니다" 같은 안내문으로 시작하는 경우가 많다 (추정). WikiTok은 썸네일이 없는 문서를 버리는데, 나무위키는 이미지 저작권 문제로 이미지가 없는 문서가 많아 남는 문서가 적을 수 있다 (추정).
3. **대체재가 무료이고 마찰도 낮다.** 헤비 유저는 이미 namu.wiki에서 바로 랜덤 문서를 볼 수 있다. namutok만의 가치가 "넘기는 UX" 하나뿐이면 한 번 써 보고 떠날 수 있다.
4. **성공할수록 깨지는 구조다.** 운영비 0원 조건에서 서버 프록시나 캐시가 필요하면, 트래픽이 늘수록 무료 한도를 넘기거나 나무위키 쪽에서 차단할 가능성이 커진다.
5. **바이럴 메시지가 약하다.** WikiTok의 화제성은 "숏폼 대신 지식"이라는 메시지에서 나왔다. 나무위키는 신뢰성 논란이 있어 같은 메시지를 쓰기 어렵다 (추정). "B급 재미"로 포지셔닝하면 쇼츠와 직접 경쟁하게 된다.
